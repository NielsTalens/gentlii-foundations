business case

Completeness: Partial

Strength: Medium

Business Rationale

Current CRM tools are described as “broken” for frontline users because they create admin overhead (clicking, field updates, dashboards), leading reps to avoid logging activities and creating untrusted/inaccurate pipeline data and shadow systems. The initiative exists to shift CRM from a “system of record” to a “system of action/execution” that reduces cognitive load and tells users what to do next.

Confidence: High

Evidence

“CRM as it exists today (like Salesforce etc.) is kind of broken… It’s too much clicking around, updating fields… feels like admin work instead of helping you sell.” / “Reps avoid logging activities… Managers don’t trust CRM data… Pipeline is inaccurate… Shadow systems… emerge” / “Shift from system-of-record… We want CRM as a system of execution.” / “We need to to reduce cognitive load, not just time”

Contradictions

The product direction de-emphasizes dashboards/insights, but a customer event lists users wanting more insights and to create their own dashboards, which could conflict with the stated rationale/design stance.

Evidence:

“they don’t want dashboards” and “We’re intentionally not doing… analytics dashboards” vs “Users want to have more insights in the process” and “Users want to create their own dashboards”.

Expected Value

Value is expected through reduced CRM fatigue and cognitive load, higher daily adoption/usage, faster onboarding (little to no training), and improved sales execution (more follow-up, fewer things falling through cracks). It also aims to improve data quality/accuracy by making logging automatic and pipeline updates happen in the background.

Confidence: High

Evidence

“reduce the general fatigue people have with CRM” / “get reps to actually use the system daily” / “increase revenue per rep (if they follow up more, this should happen)” / “make onboarding basically nonexistent or very fast” / “automatic logging… pipeline updates happening in the background” / “Pipeline is inaccurate… [today]” and “everything logs automatically… pipeline updates itself”

Contradictions

The value proposition emphasizes “actions > insights” and avoiding reporting, while some user feedback asks for more insights and custom dashboards, which may indicate misalignment on what users value.

Evidence:

“actions > insights… avoid anything that looks like reporting” vs “Users want to have more insights… create their own dashboards”.

Assumptions

The business case assumes that reducing friction (no dashboards, minimal input, conversational interface) will increase daily usage, that increased follow-up driven by “next best action” will increase revenue per rep, and that automation can reliably capture activities and keep the pipeline updated without manual input. It also assumes that minimal/no training is achievable and desirable.

Confidence: Medium

Evidence

“increase revenue per rep (if they follow up more, this should happen)” / “get reps to actually use the system daily” alongside “tell you your next best action” and “keep the pipeline updated without you touching it” / “If someone needs training, we probably failed.” / “emails + calls captured automatically… deal stage updated without asking user… basically zero data entry”

Contradictions

A strong assumption is that users “don’t want dashboards,” but separate feedback indicates at least some users want dashboards and more insights, challenging the assumption about user preferences.

Evidence:

“they don’t want dashboards” vs “Users want to create their own dashboards”.

Measurable Business Outcomes

Stated measurable outcomes include: increasing subscription revenue by EUR 50,000 per quarter, adding 20k new registered users this year, securing additional investments of EUR 200k, and improving NPS from 7 to 9. Adoption/usage and onboarding speed are stated as goals but without specific metrics/targets.

Confidence: High

Evidence

“Increase of revenu of EUR 50.000,- per quarter in subscriptions” / “New features result in 20k new registred users this year” / “Additional investments EUR 200k” / “NPS score from 7 to a 9” / (non-quantified) “get reps to actually use the system daily” and “make onboarding basically nonexistent or very fast”

Contradictions

No explicit contradictions among the numeric outcome targets were found in the provided text.

Evidence:

“No supporting evidence found”

Suggestion

  • Add explicit, testable adoption and efficiency metrics (e.g., daily active usage %, time spent in CRM, % activities auto-logged, pipeline accuracy) tied to the stated goals (“use daily”, “reduce fatigue”, “fast onboarding”).
  • Clarify the causal chain for revenue impact (how “next best action” increases follow-ups, conversion rates, and revenue) and define leading indicators to validate it.
  • Reconcile the “no dashboards/insights” stance with expressed user demand for insights/custom dashboards (define if/when insights exist, and in what “action-first” form).
  • Make key assumptions explicit as validation hypotheses (automation reliability, integration coverage for email/calls, user willingness to follow recommended actions).
  • Define onboarding success criteria (e.g., time-to-first-value, time-to-first-sent follow-up, training minutes) to support “basically nonexistent” onboarding.

product charter

Completeness: Complete

Strength: High

Core Principles

  • Conversation-first as the primary interface; avoid screens where possible.
  • Actions over insights; the product exists to drive immediate execution, not reporting.
  • Automation by default; the system captures and updates without asking the user to fill fields.
  • Reduce cognitive load by minimizing choices and decisions for the user.
  • CRM should become “invisible” over time (feels like it disappears; user just acts).

Confidence: High

Evidence

“conversation first, always… everything through chat / language, no screens if we can avoid it”; “actions > insights”; “automation by default… if user has to fill fields → something went wrong”; “We need to to reduce cognitive load, not just time”; “The best tools disappear—they don’t feel like tools.”; “Feels like CRM should become kind of invisible over time.”

Contradictions

Customer feedback indicates demand for “more insights” and “create their own dashboards,” which conflicts with the principles of “actions > insights” and “avoid anything that looks like reporting.”

Evidence:

“Users want to have more insights in the process”; “Users want to create their own dashboards” vs “avoid anything that looks like reporting.”

Product Boundaries

  • Not a reporting/BI tool.
  • Not a place to input data manually (avoid data entry/field filling).
  • Not an endlessly customizable Salesforce-like CRM.
  • Not traditional CRM UI patterns (screens/tabs/dashboards/pipeline browsing), at least initially.

Confidence: High

Evidence

“what we are not… not a reporting tool… not BI… not a place to input data… not something you customize endlessly… basically not another version of Salesforce”; “We’re intentionally not doing: traditional screens; analytics dashboards (at least not upfront); manual pipeline management.”

Contradictions

Customer feedback requesting dashboards conflicts with the “not a reporting tool / not BI” and “analytics dashboards (at least not upfront)” boundary.

Evidence:

“Users want to create their own dashboards” vs “not a reporting tool… not BI” / “analytics dashboards (at least not upfront).”

Behavioral Rules

  • System provides “next best action” and prioritizes actions to remove user decision-making.
  • System should suggest actions proactively (ideally before being asked).
  • If user asks “why this?”, provide a short explanation (not a report).
  • Logging (emails/calls) happens automatically; pipeline updates in the background.
  • Minimize choices; don’t present many options (“don’t give users 10 options”).
  • If users must do training or fill fields/manual updates, that indicates product failure.

Confidence: High

Evidence

“tell you your next best action”; “system suggests actions before you ask (ideally)”; “if you ask ‘why this?’ → short explanation, not a report”; “log stuff automatically (calls, emails etc.)”; “pipeline updates happening in the background”; “reduce choices, don’t give users 10 options”; “If someone needs training, we probably failed.”; “if user has to type things in fields, we probably failed.”

Contradictions

No contradictory content found.

Making Rules

  • Prefer removing a screen over adding one.
  • Features must enable immediate action; if it doesn’t lead to action, it probably shouldn’t exist.
  • Reduce required user input whenever possible.
  • Avoid drift toward traditional CRM patterns (tabs/dashboards).

Confidence: High

Evidence

“decision rules (gut checks): can we remove a screen instead of adding one; does this help someone take action immediately; can we reduce input here; if it doesn’t lead to action → probably shouldn’t exist”; “if we start adding tabs + dashboards we’re probably drifting.”

Contradictions

No contradictory content found.

Product Character

  • Should feel focused, direct, calm, and somewhat decisive (tells you what to do).
  • Should make users feel in control, not overwhelmed; reduce stress/guilt associated with CRM.
  • Should not feel analytical, busy/cluttered, gamified, or overly configurable.

Confidence: High

Evidence

“product should feel like: focused; direct; calm; a bit decisive”; “ideal state = calm, clear, just doing the next thing”; “should NOT feel like: analytical tool; busy / cluttered; gamified; overly configurable.”

Contradictions

No contradictory content found.

  • No hype/cheerleading language; no buzzwords.
  • Prefer action-oriented phrasing (e.g., “call these 3 deals”) over metric/report framing.

  • “If someone needs training, we probably failed” (onboarding/training as an integrity signal).
  • “If it starts looking like a traditional CRM again, we’ve probably lost the plot” (UI/shape drift check).
  • “If it doesn’t lead to action → probably shouldn’t exist” (feature acceptance test).
