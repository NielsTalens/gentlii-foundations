## Business Rationale

Current CRM tools are described as “broken” for frontline users because they create admin overhead (clicking, field updates, dashboards), leading reps to avoid logging activities and creating untrusted/inaccurate pipeline data and shadow systems. The initiative exists to shift CRM from a “system of record” to a “system of action/execution” that reduces cognitive load and tells users what to do next.

### Confidence

High

**Evidence:** “CRM as it exists today (like Salesforce etc.) is kind of broken… It’s too much clicking around, updating fields… feels like admin work instead of helping you sell.” / “Reps avoid logging activities… Managers don’t trust CRM data… Pipeline is inaccurate… Shadow systems… emerge” / “Shift from system-of-record… We want CRM as a system of execution.” / “We need to to reduce cognitive load, not just time”

### Contradictions

The product direction de-emphasizes dashboards/insights, but a customer event lists users wanting more insights and to create their own dashboards, which could conflict with the stated rationale/design stance. **Evidence:** “they don’t want dashboards” and “We’re intentionally not doing… analytics dashboards” vs “Users want to have more insights in the process” and “Users want to create their own dashboards”.

## Expected Value

Value is expected through reduced CRM fatigue and cognitive load, higher daily adoption/usage, faster onboarding (little to no training), and improved sales execution (more follow-up, fewer things falling through cracks). It also aims to improve data quality/accuracy by making logging automatic and pipeline updates happen in the background.

### Confidence

High

**Evidence:** “reduce the general fatigue people have with CRM” / “get reps to actually use the system daily” / “increase revenue per rep (if they follow up more, this should happen)” / “make onboarding basically nonexistent or very fast” / “automatic logging… pipeline updates happening in the background” / “Pipeline is inaccurate… [today]” and “everything logs automatically… pipeline updates itself”

### Contradictions

The value proposition emphasizes “actions > insights” and avoiding reporting, while some user feedback asks for more insights and custom dashboards, which may indicate misalignment on what users value. **Evidence:** “actions > insights… avoid anything that looks like reporting” vs “Users want to have more insights… create their own dashboards”.

## Assumptions

The business case assumes that reducing friction (no dashboards, minimal input, conversational interface) will increase daily usage, that increased follow-up driven by “next best action” will increase revenue per rep, and that automation can reliably capture activities and keep the pipeline updated without manual input. It also assumes that minimal/no training is achievable and desirable.

### Confidence

Medium

**Evidence:** “increase revenue per rep (if they follow up more, this should happen)” / “get reps to actually use the system daily” alongside “tell you your next best action” and “keep the pipeline updated without you touching it” / “If someone needs training, we probably failed.” / “emails + calls captured automatically… deal stage updated without asking user… basically zero data entry”

### Contradictions

A strong assumption is that users “don’t want dashboards,” but separate feedback indicates at least some users want dashboards and more insights, challenging the assumption about user preferences. **Evidence:** “they don’t want dashboards” vs “Users want to create their own dashboards”.

## Suggestion

- Add explicit, testable adoption and efficiency metrics (e.g., daily active usage %, time spent in CRM, % activities auto-logged, pipeline accuracy) tied to the stated goals (“use daily”, “reduce fatigue”, “fast onboarding”).
- Clarify the causal chain for revenue impact (how “next best action” increases follow-ups, conversion rates, and revenue) and define leading indicators to validate it.
- Reconcile the “no dashboards/insights” stance with expressed user demand for insights/custom dashboards (define if/when insights exist, and in what “action-first” form).
- Make key assumptions explicit as validation hypotheses (automation reliability, integration coverage for email/calls, user willingness to follow recommended actions).
- Define onboarding success criteria (e.g., time-to-first-value, time-to-first-sent follow-up, training minutes) to support “basically nonexistent” onboarding.
